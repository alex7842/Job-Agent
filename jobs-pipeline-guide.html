Intro — The big picture

This app searches job sites every day, saves new jobs, and AI-scores each one against your resume. It uses two different tools for two different jobs:

Temporal = the orchestrator (the boss)

Decides what should happen and when: run a search every day at 10:00, for every profile, across every job source. It starts work, retries failures, and remembers everything in its history.

Kafka = the water pipe (the data highway)

Carries each job through the pipeline like parcels on a conveyor belt: fetched → stored → scored. It lets independent processes send/receive messages without knowing each other.

Why two processes?

  • Process #1 = npm run start:dev — the HTTP API and the Kafka consumers. You need this always running so the website works.
  • Process #2 = npm run dev:worker — the Temporal worker. It only runs the daily search + fetches from job sites. You can run several of these, or none (then scheduled runs just wait).

They never call each other directly. They meet only through Kafka and Temporal — that is the whole point: in production you can have 3 API replicas and 5 workers, and it still works the same.

Part 1 — Kafka, from zero

Kafka is a distributed log. Think of a binder: every message is a page that is added at the end of a notebook and never changed. When a consumer reads, it just follows the pages.

Analogy: a Topic is a playlist. It is split into Partitions = separate playlists on separate speakers. Multiple speakers can play different songs simultaneously (parallelism). Each playlist keeps its own order.

1.1 Partitions and keys — the heart of Kafka

A topic with 3 partitions (jobs.raw in this app)

Every message is stored in exactly one partition, at the end. Offsets are per partition, so partition 1 can have offset 7 while partition 2 has offset 2.

Partition 0
key=profileB · job 1offset 0
key=profileC · job 1offset 1
key=profileB · job 2offset 2 (newest)
Partition 1
key=profileA · job 1offset 0
key=profileA · job 2offset 1 (newest)
Partition 2
… empty …—

Notice: messages with the same key (e.g. profileA) sit in the same partition, in order. profileB is in partition 0. profileC in partition 0 too — that is fine, they are just neighbours.

How does Kafka choose the partition?

A producer can send a message with a key, e.g. key = profileId (that is what this app does: emit(topic, profileId, evt)).

key "profileA"message
→hash(key)
hash % 3→ partition number
→
Partition 1always

The rule: partition = hash(key) mod (number of partitions). Same key → same hash → same partition, always. That gives you two superpowers:

  • Order per key — all messages of one profile arrive in order. Job 1 is always processed before job 2 of the same profile.
  • Fair(ish) spreading — different profiles land on different partitions and are processed in parallel.

Warning you saw in the logs — "KafkaJS v2 switched default partitioner…" KafkaJS changed which hash function it uses, but the rule above is unchanged: same key → same partition. It only matters if you mix producers with different hashing algorithms and still expect identical partition numbers — which you almost never care about.

Why 3 partitions here?

In kafka.config.ts every pipeline topic is created with numPartitions: 3 (the DLQ gets 1). Why 3?

  • You can only process as many messages simultaneously as you have consumers × partitions. 3 partitions = up to 3 parallel consumers per group. That is "good enough" for a practice app.
  • More partitions = more parallelism, but also more files / more overhead on the broker. For most apps 3–10 is plenty.

Biggest Kafka mistake (know it early): a topic's partition count can be changed later (Kafka lets you add partitions), but adding partitions changes which partition a key lands in for the new count. So you cannot rely on "key X was in partition 1 forever". You can rely on "at any given moment, key X is in one specific partition".

1.2 Consumer groups — how parallel workers split partitions

Consumers that share the same groupId form a group. Your whole topic's partitions are exactly divided among the members of the group. This is the part that makes Kafka scale.

Same group "job-pipeline-server", different number of consumers:

SetupPartition assignmentResult
1 consumer Consumer A gets partitions 0,1,2 Everything processed, but one by one (limited parallelism)
2 consumers A gets 0,1  ·  B gets 2 2x faster. Each partition still processed by exactly one member.
3 consumers A→0  ·  B→1  ·  C→2 Full parallelism per partition.
4 consumers A→0, B→1, C→2, D→nothing Consumer D sits idle — cannot happen

Rule: a partition is processed by one consumer at a time. So max useful consumers = number of partitions. Extra consumers just idle.

Topic jobs.rawP0 · P1 · P2
★
Consumer Areads P0
★
Consumer Breads P1
★
Consumer Creads P2

★ = the group leader (chosen automatically among members) decides the split. If A crashes, its partitions are handed to B and C (rebalance).

Practical scaling rule for this app: if scoring is slow, start more API instances sharing group job-pipeline-server — up to 3 of them get partitions. Beyond that, increase partition count (or split the work differently).

1.3 Offsets and the "at-least-once" promise

Every consumer remembers, per partition, the offset of the last message it finished. It "commits" that number so that if it dies, the next consumer continues from there.

Partition 00·1·2·3·4·5·6·7
→committed up to offset 5
Consumer reads 6,7then commits 7

In this app the consumer uses KafkaJS auto-commit: it commits every few seconds, after processing. So by default it commits after your handler finished — but a crash in that tiny window still causes a duplicate.

This is the most important thing to internalise: Kafka gives at-least-once, not exactly-once. Your onRaw handler can run two times for the same job. That is why the app is built idempotent:

Where duplicates can enterHow this app stays safe
Producer retries a send (network blip) → same job published twice DB unique constraint on (profileId, dedupeHash) + INSERT … ON CONFLICT DO NOTHING (insertIfNew) → second insert is ignored.
Consumer processed but died before committing offset → redelivery Same dedupe constraint → no duplicate row.
Scoring event redelivered → job scored twice (money!) if (job.scoredAt) return; in onNew — already scored → skip.
User clicks "rescore" twice Same scoredAt guard + dedupe. Worst case one extra LLM call, never a corrupt row.

Edge case — consumer group "from latest" can miss messages: this app subscribes with fromBeginning: false, meaning a brand-new consumer group starts at the latest offset. If you have no API running during a scheduled run, the fetched jobs are still produced to jobs.raw. When you start the API again with a fresh group, it starts from "now" and skips those old messages (they do not expire immediately — they just aren't re-read). For a permanently-running service this is fine. If you want "process everything ever produced even if I was offline", use fromBeginning: true (and keep consumers running).

Part 2 — Temporal and the "worker"

Temporal answers: "make sure this multi-step job happens, and if anything breaks halfway, finish or retry it."

2.1 The two kinds of code

Workflow code (workflows.ts)
decides the steps
must be deterministic — no random(), no Date.now(), no external calls
is recorded in Temporal's history (replayable)
calls activities via proxyActivities
Activity code (activities.ts)
does the real work: HTTP fetch, DB write, Kafka publish
can use any library, any code
has timeouts + retries configured by the workflow
returns small results (a count) that go into history

Why this split? Because a Temporal workflow can run for months and must survive crashes. The server stores every "event" (activity started → result returned). If the worker dies, a new worker reloads the history and replays it to know where to continue. That only works if workflow code is a pure, deterministic script. All real I/O lives in activities.

2.2 What a "worker" actually is

A worker is just a process (like our worker.ts) that says: "I am available for the task queue job-search. Give me workflows and activities." The Temporal server decides who gets what.

Any number of workers can poll the same queue. Unlike Kafka there is no "partition per consumer" limit — Temporal hands out tasks to whoever is free. More workers = more work done in parallel.

2.3 Scaling a Temporal worker

You scale in two dimensions:

  • More worker processes — just run npm run dev:worker on more machines/containers, all pointing at the same Temporal address + task queue. Nothing else changes.
  • More concurrency inside one worker — one worker is multi-threaded and can run several workflows and activities at once. You control it in Worker.create() options:
// worker.ts
const worker = await Worker.create({
  taskQueue: TASK_QUEUE,
  maxConcurrentWorkflowTaskExecutions: 100,  // how many workflows this process juggles
  maxConcurrentActivityTaskExecutions: 50,   // how many HTTP fetches at the same time
  // maxConcurrentLocalActivityExecutions,
  // activitiesPerSecond: 10,
});

Edge case — the API hitting itself during a peak: our fetchAndPublish activity opens real HTTP connections to job sites. If you raise activity concurrency a lot, you may hammer those APIs and get 429 (rate limited). Mitigation = activitiesPerSecond (a token bucket) or per-activity retry with backoff (already configured: initialInterval 10s → backoff ×2 → max 2min, 4 attempts).

2.4 Sticky execution — one small trick

Temporal likes to give related tasks to the same worker (this is called sticky cache) so it can reuse loaded workflow code instead of re-downloading history. It is automatic — just don't be confused when the Temporal UI shows a workflow "stuck" on one worker in the logs.

2.5 The schedule (the "daily at 10:00" part)

In temporal-client.service.ts, ensureSchedule() creates a Schedule: cron 0 10 * * * in Asia/Kolkata, overlap: SKIP.

Manual trigger: POST /runs calls temporal.startRun(profileId) → same workflow, identical behaviour as the 10:00 run. This is how you test the whole pipeline by hand.

Why each step exists (the design reasoning)

StepWhy it is separateWhat breaks if you remove it
Temporal workflow + activities Retries/backoff for fragile HTTP fetches, keeps a search-run record per day, survives crashes A failing source would kill the whole daily run with no retry, and you'd lose the audit trail
jobs.raw → jobs.new Fetching (slow, many) is decoupled from storing (fast, deduped) A slow source would block/slow storing; duplicates would pile up because dedupe wouldn't run per-message
jobs.new → jobs.scored LLM calls are costly + slow; they must be retried idempotently and must never block ingestion A slow/violating LLM would back up the queue and never store; you'd pay for duplicate scoring on redelivery
jobs.dlq A poison job (malformed / LLM out of context / DB hiccup) goes to its own box One bad message would be retried forever / block its partition / flood your logs

The "search run" bookkeeping: the workflow calls startRun() (creates a search_runs row) and finishRun() (writes {source: {fetched, error?}} + status completed/partial/failed). This gives you a daily report of which platform worked — without reading any job payloads.

Part 4 — Edge cases, sorted by "what can actually bite you"

Kafka side

Edge caseWhat happensHow this app survives / what to do
Duplicate message (producer retry / consumer crash → redelivery) Same job arrives 2× Unique (profileId, dedupeHash) + ON CONFLICT DO NOTHING → stored once. scoredAt guard → scored once.
Poison message (job that always throws) Handler throws, message retried Caught → pushed to jobs.dlq, consumer keeps moving. Score errors also saved on the row as scoreError.
Consumer crashes mid-message Offset not committed → message redelivered At-least-once + idempotency = acceptable duplicate, no loss.
API offline during a scheduled run Jobs published to jobs.raw, nobody reading them Messages sit on the broker (retention ~days–weeks). New consumer with fromBeginning:false starts at latest → those messages are skipped. Decide deliberately: keep an API always on, or flip to fromBeginning:true.
Hot key / partition skew One profile has way more jobs → its partition is busier than others Ordering still holds (good). Over time that partition lags. Mitigation: more partitions, or a more granular key (e.g. profileId | source) — but then per-profile order can interleave across sources.
Kafka down at API boot ensureKafkaTopics() fails → API fails to start Current design: hard requirement. For resilience you could catch and retry, or boot HTTP-first and connect consumers later (more code).
Auto-created topic vs configured partitions Broker may auto-create a topic with 1 partition if it doesn't exist ensureKafkaTopics() runs on boot and creates the right counts (3 / DLQ 1). Don't rely on auto-creation.
Group rebalance storms (many restarts) Each join/leave reassigns partitions, briefly pausing processing KafkaJS default session.timeout + our 1 consumer group. Restarting the API frequently causes tiny rebalances — harmless here; in prod prefer rolling deploys.

5.6 Scale it — answer these 3 questions

"It's slow because…"Answer
too many jobs queued/un-scoredRun more API replicas sharing group job-pipeline-server (max 3 without adding partitions) — each handles a partition in parallel.
fetching takes forever / scraping hits rate limitsAdd worker concurrency (maxConcurrentActivityTaskExecutions) or throttle (activitiesPerSecond); add more workers on the same queue.

Cheat sheet — one-line rules to remember

  • Same key → same partition → order preserved for that key.
  • Max active consumers per group = number of partitions.
  • Kafka = at-least-once → your handlers MUST be idempotent. (Dedupe-constraint + scoredAt guard.)
  • Poison messages go to the DLQ, never block the pipe.
  • Workflow = deterministic; Activity = real I/O + retries.
  • More Temporal workers = more parallel work; no partition limit.
  • Schedules: overlap SKIP, idempotent create, manual POST /runs for testing.
  • If you were offline and use fromBeginning:false, old Kafka messages are skipped — decide deliberately which behaviour you want.
